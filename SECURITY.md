# Clasp Security

## Threat model and boundary

Clasp is a single-user, local-first macOS app. Its Vault is designed to keep sensitive note content unreadable on disk while the Vault is locked and to detect modification or corruption of its encrypted container. It assumes macOS, the user account, Keychain, CryptoKit, and the running app binary are trusted.

The Vault is not a defense against malware or another person controlling an already-unlocked Mac. It does not claim to prevent screenshots, privileged memory inspection, keystroke capture, clipboard-manager retention, backups made while data is plaintext, or forensic recovery after deletion on APFS/SSD storage.

Credentials, API keys, and recovery codes are better stored in a dedicated password manager. If they are stored in Clasp, they must be Vault notes—not regular notes.

## Regular notes

In local and direct builds, regular notes are UTF-8 Markdown under `~/Library/Application Support/Personal Notepad/Notes/`; the App Store build resolves the same logical folder inside its sandbox container after the controlled migration gate. Clipped images are stored under `Notes/Attachments/`. Their bodies, image bytes, locally recognized image text, titles, tags, organizational state, and timestamps are plaintext by design. A versioned JSON index provides fast loading and can be rebuilt from the Markdown files and atomic sidecars.

Writes use atomic replacement at the store boundary. Regular notes are portable and understandable, but anyone or any process with access to the user's files can read them. Do not put secrets in regular notes.

## Vault encryption and Keychain

The Vault uses a cryptographically random 256-bit key generated by CryptoKit. Before creating or retrieving it, Clasp asks macOS Local Authentication to verify device-owner presence using Touch ID when available or the login password. The key is stored as a generic-password Keychain item for service `com.robertmoore.personalnotepad.vault`, protected with:

- explicit `LocalAuthentication.deviceOwnerAuthentication` before Clasp reads or creates the key;
- `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, so the item is unavailable while the device is locked and does not migrate to another device.

This split design is intentional for the local ad-hoc build. Data-protection Keychain access-control items require restricted signing entitlements and an Apple-issued identity; forcing them in an ad-hoc build fails with `errSecMissingEntitlement`. The standard per-user Keychain plus explicit Local Authentication preserves user-presence verification without weakening macOS launch trust or requiring a Developer account.

Vault content is serialized and encrypted with CryptoKit AES-GCM. Every encryption operation generates a fresh random nonce. Only a format version and an opaque ciphertext blob are outside the authenticated ciphertext. Titles, tags, bodies, image attachments, locally recognized image text, organizational metadata, and timestamps are all encrypted.

AES-GCM authentication failure, a wrong key, malformed serialization, or an unsupported format version fails closed. No partial plaintext is returned. Vault plaintext is decoded only into memory; no plaintext Vault file or temporary file is intentionally created.

The encrypted container is atomically written to the logical `Personal Notepad/Vault/vault.pnvault` application-support location: the ordinary user Application Support path for local/direct builds and the sandbox-container path for the App Store build.

Vault Trash is soft deletion, not immediate erasure. Trashed Vault notes remain encrypted inside the same container and are included in encrypted exports until they are permanently deleted. They are visible for recovery only while the Vault is unlocked; locking removes them from Trash and all other shared views. Permanent deletion rewrites the encrypted container without the deleted record, but Clasp makes no secure-erasure or forensic-recovery guarantee on APFS/SSD storage.

## Locking behavior

Explicit lock is available in the toolbar, Capture menu, sidebar context menu, menu bar extra, and with `Control-Option-Command-L`.

The Vault also locks when:

- macOS is about to sleep;
- the user session resigns active, including fast-user switching;
- the screen-lock notification is received;
- the inactivity timer expires;
- the app terminates.

The default inactivity timeout is 10 minutes. Settings offer 1, 5, 10, or 30 minutes, or Never. The UI warns that Never retains decrypted state until an explicit/system lock. Locking removes all decrypted Vault note models from observable application state and clears the cached in-memory key reference.

## Clipboard behavior

Clipboard capture accepts text and normalized PNG images. The explicit **Add Clipboard to Clasp** action routes to the plaintext Inbox; **Add Clipboard to Vault** routes to encrypted storage. Content classification never decides whether content is secret—the user always chooses the destination. The app never stores clipboard history and does not repeat captured contents in status messages or logs.

Styled text capture accepts size-bounded RTF and HTML. HTML is converted through a narrow local sanitizer that removes scripts, stylesheets, embedded media, frames, objects, metadata, and all unsupported tags before Markdown rendering. Only `http`, `https`, and `mailto` links are retained. Clasp does not use a web view or fetch remote resources to import formatting.

Vault clipboard capture saves the current text or image and schedules clipboard clearing unless Settings is set to Never. The default delay is 30 seconds; Settings offer immediate, 15, 30, or 60 seconds, or Never. When enabled, clearing occurs only if both the captured content and pasteboard change count still match the snapshot, so newer clipboard contents are preserved. Images are normalized to PNG and limited by compressed size, dimensions, and total pixel count before capture; recognized text is also length-bounded.

This cannot erase copies already retained by a clipboard manager or another process.

## Selection-shortcut permission (local/direct builds only)

The global `Control-Option-N` and `Control-Option-P` shortcuts in local/direct builds need macOS Accessibility approval because Clasp posts one `Command-C` event to the frontmost app when a shortcut is pressed. Clasp does not install an event tap, listen to keystrokes, or monitor selection changes. The Mac App Store build compiles this implementation out and uses Services only.

Before issuing Copy, Clasp attempts a bounded, complete snapshot of the available pasteboard items and types. If complete preservation exceeds its item, type, per-value, per-item, or aggregate byte budgets—or any value cannot be copied—the selection shortcut fails closed before issuing Copy. After a complete snapshot, Clasp reads the new selected text, link, styled text, or image once and restores the old clipboard only if the pasteboard still contains the shortcut-generated copy. If another copy occurs during capture, Clasp leaves that newer clipboard untouched. A clipboard manager may still retain the brief copied selection.

The right-click `NSServices` actions do not require Accessibility permission and remain available as the least-privilege fallback. Accessibility access can be revoked at any time under System Settings › Privacy & Security › Accessibility.

## Auto-save, logs, and network surface

Automatic organization is local and deterministic. Text classification uses conservative content signals. Image text recognition uses Apple's on-device Vision framework. No note, image, recognized text, or tag is transmitted for classification. Automatic tags remain editable and are not a security classification.

Regular and Vault edits are autosaved after a short debounce with atomic persistence. Local and Mac App Store builds contain no network client or third-party SDK. The separately compiled direct-download channel uses exact-pinned Sparkle only to retrieve an HTTPS appcast and signed app update; it does not transmit note, Vault, clipboard, account, analytics, or telemetry data. Update archives and the feed are EdDSA-signed, and the app is configured to verify the update before extraction. Unified-log modes exist only for local troubleshooting. The app does not intentionally log bodies, clipboard values, titles, tags, keys, recovery keys, or other encryption material.

## Encrypted export and recovery

Vault export generates an independent random 256-bit recovery key and AES-GCM-encrypts the complete Vault payload. The exported JSON contains only a format version and opaque ciphertext; it contains no plaintext title, tag, body, or timestamp. The recovery key is displayed once and is not persisted by the app.

Import requires the exported file and recovery key. The export must authenticate and decode completely before it is accepted. Before replacing the current Vault, the app preserves its encrypted container as `vault.previous.pnvault`, then encrypts imported records under the local Keychain-protected key. If no local key exists—as on a new installation—the app creates a fresh random user-presence-protected Keychain key only after the export has authenticated.

There is no recovery service or backdoor. Losing the recovery key makes that export unrecoverable. Store the exported file and recovery key separately.

## Reporting and operational guidance

Clasp does not yet have a hosted public security-reporting endpoint. Before any public distribution, the final Support URL and monitored contact must provide a clear route for vulnerability reports; until that release gate is closed, this file must not be read as offering a public reporting channel. If suspicious corruption is detected, keep the encrypted files, stop editing the Vault, and restore from a known-good encrypted export. Do not share Vault files together with their recovery keys.
